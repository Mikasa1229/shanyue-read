# Reader 单实例接口压测完整报告

## 1. 先看结论

这是一次面向单实例 Demo 和面试展示的真实本地 HTTP 压测，不是生产容量承诺。

本轮最新扩展测试使用 8 个本地/安全接口，采用 `1、25、100、400` 四个并发档位，每档持续 3 秒。所有这些接口在本轮测试中都返回了预期状态，未出现连接错误或超时。

最重要的结果：

| 接口类别 | 代表接口 | 100 并发 | 400 并发 | 结论 |
| --- | --- | --- | --- | --- |
| 小说分页 | `/api/novels?page=1&size=20` | 868.33 QPS，p95 160.10 ms | 1012.67 QPS，p95 463.71 ms | 100~400 并发出现明显排队 |
| 排行榜缓存 | `/api/reading/ranking?page=1&size=20` | 3247.33 QPS，p95 48.21 ms | 3105.67 QPS，p95 118.01 ms | 缓存读路径吞吐较高 |
| 书源分页 | `/api/book-sources?page=1&size=20` | 293.67 QPS，p95 405.84 ms | 374.67 QPS，p95 1668.10 ms | 当前测试数据下最慢的本地读接口 |
| 网关鉴权 | `/api/auth` | 3648.33 QPS，p95 44.08 ms | 3386.33 QPS，p95 102.20 ms | 轻量过滤路径，不能代表登录后业务 |

按本 Demo 的体验验收口径：

```text
错误率 < 1%
p95 < 200 ms
p99 < 500 ms
```

可以得到以下建议：

- 小说列表建议把 `100 并发`附近作为当前单实例的稳定体验档位；到 `400 并发`时 p95 已接近 464 ms；
- 书源分页在 `25 并发`时 p95 已达到 156.39 ms，`100 并发`超过 400 ms，应优先检查数据库查询和响应组装；
- 排行榜在 `400 并发`时仍满足本次 p95/p99 口径，但这是短窗口缓存读测试；
- 未登录接口返回 `401` 是预期鉴权结果，不能把它当成业务失败，也不能用它代表 Agent 对话能力；
- 书源搜索会访问外部网站，必须单独分析超时和外部依赖可用性，不能和本地接口混算 QPS。

## 4. 压测参数含义

### 4.1 并发数（Concurrency / Workers）

并发数表示同时运行的请求工作单元数量。例如 `100` 表示最多有 100 个线程工作单元同时发请求。

它不等于真实用户数：一个用户可能每几秒才发一个请求，一个工作线程在压测中则会尽可能连续发请求。

本轮并发档位：

```text
1、25、100、400
```

上一轮基础压测还测试过：

```text
10、50、200、800
```

### 4.2 持续时间（Duration）

本轮扩展测试每档持续 `3 秒`。它用于控制每个并发档位的采样窗口。

3 秒适合快速发现趋势，但有明显局限：

- 不能证明 10 分钟长稳能力；
- 不能充分暴露内存泄漏、连接泄漏和缓存失效；
- 可能受到 JIT、GC 和瞬时调度影响。

基础极限测试使用过每档 `5 秒`，结果保存在 `logs/real-load-test.json` 和 `logs/real-load-test-800.json`。

### 4.3 阶梯（Stages）

阶梯就是按多个并发档位依次测试，而不是一开始直接打到最大压力：

```text
1 → 25 → 100 → 400
```

这样可以观察：

- 吞吐是否随着并发增加而增加；
- 哪一个档位开始排队；
- p95/p99 是否突然恶化；
- QPS 是否进入饱和区。

### 4.4 Ramp-up / 升压时间

JMeter 中的 `Ramp-up` 表示把目标线程逐渐启动起来的时间。例如：

```text
线程数 = 100
Ramp-up = 10 秒
```

表示大约用 10 秒逐渐启动 100 个线程，而不是同一毫秒全部启动。升压可以减少瞬时启动尖峰，更接近用户逐渐进入系统的情况。

当前 JMeter 计划默认：

```text
THREADS = 100
RAMP_SECONDS = 10
DURATION = 120
```

这些参数可以命令行覆盖。

### 4.5 请求超时（Timeout）

Python 执行器的单请求超时设置为 `10 秒`。超过 10 秒仍未建立或完成请求，会记录为 `TimeoutError`。

超时不是普通的高延迟：

- 高延迟但最终完成：计入请求数和延迟分布；
- 超时：计入错误数，不计为预期成功；
- 连接被拒绝或重置：计入错误数，并记录异常类型。

### 4.6 Keep-Alive / 连接复用

测试请求读取完整响应体，并尽量复用 HTTP 连接。连接复用可以减少每次请求重新建立 TCP 连接的开销，更接近浏览器或服务间调用的常见情况。

### 4.7 请求参数

本轮主要使用：

```text
小说列表：size=20
排行榜：size=20
热门书架：top=20
书源分页：page=1,size=20
```

`size` 或 `top` 越大，响应数据和序列化开销通常越大，不能把 `size=1` 的 QPS 直接代表 `size=100`。

### 4.8 预期状态码

测试工具必须知道哪些状态是业务预期：

| 接口 | 预期 HTTP 状态 |
| --- | ---: |
| 正常公开读取接口 | 200 |
| 未登录接口 | 401 |
| 不存在小说详情 | HTTP 200，JSON 内业务 `code=404` |

项目使用统一响应包装，因此业务错误不一定对应 HTTP 4xx。报告必须同时区分 HTTP 状态和 JSON 业务码。

## 5. 指标含义

### 5.1 请求数（Requests）

测试窗口内完成或记录到的请求总数。它是计算 QPS 的分子。

### 5.2 成功数（OK）

返回预期状态或满足业务断言的请求数。例如 `/api/auth` 返回 401，在本次测试中属于 OK。

### 5.3 错误数（Errors）

没有达到预期的请求数量，包括：

- 5xx；
- 错误的 2xx/4xx 状态；
- 连接拒绝；
- 连接重置；
- 超时；
- 不满足业务 JSON 断言。

### 5.4 成功率和错误率

```text
成功率 = OK / Requests × 100%
错误率 = Errors / Requests × 100%
```

本次本地核心接口的错误率为 `0%`。这只说明短时间内请求完成且状态符合预期，不说明延迟一定健康。

### 5.5 QPS

QPS 是每秒完成的请求数：

```text
QPS = Requests / DurationSeconds
```

例如 3 秒完成 3038 个请求：

```text
3038 / 3 = 1012.67 QPS
```

QPS 越高表示吞吐越高，但必须和 p95、p99、错误率一起看。继续加并发后 QPS 不增加、延迟却增加，通常表示系统进入饱和区。

### 5.6 p50

将所有请求按延迟排序后，50% 请求不超过该值。它代表典型请求体验。

### 5.7 p95

95% 请求不超过该值，只有最慢的 5% 超过它。p95 比平均值更能反映大多数用户的体验，也是本报告的主要验收指标。

### 5.8 p99

99% 请求不超过该值，只有最慢的 1% 超过它。它用来观察长尾，例如线程排队、数据库连接等待、GC 或偶发网络抖动。

### 5.9 最大延迟（max）

本次窗口中观测到的最大单请求延迟。它很容易被一次调度抖动或超时前请求影响，不能单独用来判定容量，但可以帮助发现极端长尾。

### 5.10 吞吐拐点

当并发继续增加时，如果出现下面的组合，就说明接近拐点：

```text
QPS 增长变慢或下降
p95/p99 快速上升
错误率开始上升
```

本项目小说列表的拐点大约在 `100~200` 并发之间；书源分页接口在更低并发就表现出较高延迟。

## 7. 外部书源搜索异常场景

接口：`GET /api/book-sources/search?keyword=剑来`

这个接口不能与本地接口合并分析。扩展试跑中观察到：

- 并发 1 时请求耗时约 3 秒；
- 并发 25 时部分请求成功，部分请求达到 10 秒超时；
- 并发 100 和 400 时超时比例显著增加。

这说明当前书源搜索受到外部网站响应、网络链路或服务端超时配置影响。这里的结论是“外部依赖场景需要隔离和限时”，而不是“本地 Reader 只能承载几十 QPS”。后续应单独统计：

```text
外部源成功率
单源耗时
整体超时率
并发扇出数量
失败源数量
降级返回时间
```

## 8. JMeter 容器化方案

JMeter 测试文件位于：

```text
perf/jmeter/Dockerfile
perf/jmeter/docker-compose.yml
perf/jmeter/reader-api-step-load.jmx
perf/jmeter/reader-api-endpoints.csv
```

构建固定版本镜像：

```powershell
docker compose -f perf/jmeter/docker-compose.yml build
```

运行默认测试计划：

```powershell
docker compose -f perf/jmeter/docker-compose.yml run --rm jmeter
```

指定 100 线程、10 秒升压、120 秒持续：

```powershell
docker compose -f perf/jmeter/docker-compose.yml run --rm `
  jmeter -n `
  -t /tests/reader-api-step-load.jmx `
  -JBASE_HOST=host.docker.internal `
  -JBASE_PORT=8080 `
  -JTHREADS=100 `
  -JRAMP_SECONDS=10 `
  -JDURATION=120 `
  -l /tests/output/reader-api-100.jtl `
  -e -o /tests/output/report-100
```

参数说明：

- `-n`：非 GUI 模式，适合正式压测；
- `-t`：指定 JMX 测试计划；
- `-JTHREADS`：目标线程数，近似并发工作单元数量；
- `-JRAMP_SECONDS`：逐步启动线程的时间；
- `-JDURATION`：测试持续秒数；
- `-l`：保存原始 JTL 结果；
- `-e -o`：根据 JTL 生成 HTML 报告；
- `JVM_ARGS`：可以设置 JMeter 自身的堆内存，例如 `-Xms512m -Xmx512m`。

JMeter 计划会读取 `reader-api-endpoints.csv` 的接口矩阵，并按第二列进行 HTTP 状态断言。对于统一响应中的业务码，需要增加 JSON 断言，不能只依赖 HTTP 状态。

## 9. 如何判断极限

“极限”有两种不同定义：

### 9.1 崩溃极限

系统开始出现大量 5xx、连接拒绝、超时或服务不可用时的压力。短窗口本次没有测到这个极限。

### 9.2 稳定体验极限

在规定持续时间内，同时满足：

```text
错误率 < 1%
p95 < 200 ms
p99 < 500 ms
```

对于 Demo，稳定体验极限更有解释价值。当前结果显示：

- 小说列表约在 100~200 并发之间出现拐点；
- 书源分页在 25~100 并发之间已经超过 p95 200 ms；
- 排行榜和鉴权路径在 400 并发短窗口内仍满足延迟口径。

## 10. 局限性

- 每档 3 秒，不能证明长稳运行；
- 当前小说和排行榜数据规模很小，且返回记录较少；
- 压测器和服务在同一台机器，会竞争 CPU；
- 本次没有同步导出 JVM、Tomcat、Hikari、PostgreSQL、Redis 的时间序列；
- JMeter 容器方案已准备，但本轮扩展原始数据由 Python 执行器生成，不能把本轮结果描述成“JMeter 已执行”；
- Agent SSE、模型、Milvus、Elasticsearch、Neo4j 和 RabbitMQ 索引链路没有加入本轮普通 QPS；
- 外部书源搜索的超时受互联网和第三方站点影响，不能作为本地服务吞吐结论。

> 这是一个单实例 Demo，我使用网关入口做了只读接口和鉴权接口的阶梯压测，分别统计请求数、QPS、成功率、p50、p95、p99 和最大延迟。小说列表在 100 并发时约 868 QPS、p95 160 ms，提升到 400 并发后 p95 达到 464 ms，说明 100 到 400 并发之间出现排队拐点。书源分页由于查询和响应组装更重，在 100 并发时 p95 已超过 400 ms。排行榜缓存路径在 400 并发时约 3106 QPS、p95 118 ms。未登录接口返回 401 是预期鉴权结果。书源搜索单独统计，因为它会访问外部站点；Agent SSE 则计划用 Mock 模型测试首 Token 延迟和长连接数，没有直接消耗真实模型额度。
