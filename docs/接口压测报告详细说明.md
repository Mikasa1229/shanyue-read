# 项目接口压测报告详细说明

## 1. 报告目的

本报告用于解释项目现有接口压测数据的来源、测试方法、指标含义、结果边界和后续容量评估方法。

本次压测的重点不是直接宣布“项目最大 QPS”，而是回答以下问题：

1. 网关和普通读接口在不同并发数下是否能够稳定返回；
2. 延迟是否会随着并发增长而明显恶化；
3. 哪些接口主要受数据库影响，哪些接口主要受缓存影响；
4. 当前数据能否作为本地开发环境的性能基线；
5. 生产环境还需要补充哪些长稳、阶梯和依赖隔离测试。

## 2. 测试环境

| 项目 | 本次环境 |
| --- | --- |
| 部署方式 | Windows 本地开发机，单实例服务 |
| 入口 | `http://localhost:8080` 网关 |
| Java | JDK 17 |
| 应用 | Spring Boot 微服务 |
| 数据库 | PostgreSQL（项目本地依赖） |
| 中间件 | Docker 中的 Redis、RabbitMQ 等，具体是否命中缓存取决于接口和数据状态 |
| 测试时长 | 每个并发档位约 5 秒；部分复测使用 10 秒窗口 |
| 测试脚本 | `scripts/load-test-qps.ps1`，历史结果中还包含一次 Python 并发探测结果 |

本地环境适合建立回归基线，但不适合直接推导云服务器的最终承载量。原因包括：本地 CPU、磁盘、Docker 网络、数据库缓存、服务日志配置和云服务器规格都不同。

## 3. 测试接口和业务含义

### 3.1 小说列表

```http
GET /api/novels?page=1&size=1
GET /api/novels?page=2&size=20
```

该接口用于观察网关、小说服务、PostgreSQL 查询、分页组装和可能的缓存链路。`size=1` 更接近轻量列表请求，`size=20` 更接近前端首页或搜索结果页的真实返回规模。

### 3.2 阅读排行榜

```http
GET /api/reading/ranking?page=1&size=20
```

该接口通常更容易命中 Redis 或其他缓存，因此 QPS 往往高于小说列表。它可以作为缓存读路径的性能基线，但不能代表所有业务接口的吞吐能力。

### 3.3 未登录鉴权探测

```http
GET /api/auth
```

该请求预期返回 `401`，`401` 在本测试中不是失败，而是接口按照鉴权规则正常拒绝未登录请求。该接口主要测试网关过滤器、鉴权链和轻量 HTTP 处理能力，不能代表登录后业务接口或 Agent 接口的能力。

### 3.4 未纳入本次普通 QPS 的接口

以下接口没有直接加入无控制的高并发循环：

- Agent SSE 对话；
- DeepSeek 或其他模型调用；
- 推荐生成；
- 图谱重建；
- 向量写入、全文索引和 LightRAG 重建；
- 会产生积分扣除、阅读进度写入或用户数据变更的接口。

这些接口会消耗外部模型额度、占用长连接、写入数据库或改变业务数据。它们应该使用测试用户、Mock 模型和独立测试数据库单独压测，不能和普通只读接口混在一次测试中。

## 4. 指标定义

### 4.1 并发数

并发数是同时运行的请求工作单元数量，不等于真实在线用户数。例如并发 100 表示最多有 100 个测试工作单元同时发请求，一个用户在真实场景中可能只产生很低的请求频率，因此不能直接把“并发 100”解释为“支持 100 个用户”。

### 4.2 QPS

```text
QPS = 测试窗口内完成的请求数 / 测试窗口秒数
```

报告中的 QPS 是观测吞吐，不是理论最大值。若测试窗口只有 5 秒，启动抖动、JIT、连接建立和偶发 GC 都可能对结果产生较大影响。

### 4.3 成功率

成功率按接口的预期 HTTP 状态码计算：

- 小说列表、排行榜：预期 `200`；
- 未登录鉴权探测：预期 `401`；
- 超时、连接异常、5xx、错误状态码均计为失败。

```text
成功率 = 符合预期状态码的请求数 / 总请求数
```

### 4.4 分位延迟

| 指标 | 含义 |
| --- | --- |
| p50 | 一半请求的延迟不超过该值，代表典型体验 |
| p95 | 95% 请求的延迟不超过该值，代表大多数用户体验 |
| p99 | 99% 请求的延迟不超过该值，用于观察长尾 |
| max | 本次窗口观测到的最大延迟，容易受调度、GC 或网络瞬时抖动影响 |

生产容量评估不应该只看平均延迟或最高 QPS，至少需要同时观察成功率、p95、p99 和持续时间。

## 5. 已有实测结果

### 5.1 小说列表：`size=1`

| 并发 | QPS | 成功率 | p50 | p95 | p99 | 最大延迟 |
| ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 1 | 37.38 | 100% | 30.43 ms | 33.21 ms | 36.62 ms | 49.32 ms |
| 10 | 521.44 | 100% | 17.99 ms | 35.40 ms | 41.00 ms | 50.23 ms |
| 25 | 815.73 | 100% | 30.27 ms | 49.49 ms | 57.51 ms | 69.08 ms |
| 50 | 852.06 | 100% | 57.41 ms | 84.61 ms | 99.71 ms | 128.16 ms |
| 100 | 878.58 | 100% | 110.50 ms | 155.60 ms | 180.52 ms | 270.23 ms |

解释：

- 并发从 1 增加到 25 时吞吐快速提升，说明低并发阶段主要受请求调度和连接利用率影响；
- 并发 50 到 100 后 QPS 增长变慢，而 p95 从约 85 ms 上升到约 156 ms，说明服务开始接近某个资源瓶颈；
- 在本次短窗口中没有出现错误，但这只能说明“100 并发、短时间”仍可完成，不代表继续加压仍然稳定；
- 重点观察对象应是 PostgreSQL CPU、连接池等待、Tomcat 工作线程和 SQL 执行时间。

历史复测中，`size=20` 在并发 100 时约为 `951 QPS`，p50 约 `105.01 ms`，p95 约 `135.32 ms`，p99 约 `158.89 ms`。这组数据与 `size=1` 不应直接横向比较，因为返回体大小、SQL 扫描量、缓存状态和测试脚本可能不同。

### 5.2 阅读排行榜：`size=20`

| 并发 | QPS | 成功率 | p50 | p95 | p99 | 最大延迟 |
| ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 10 | 1038.60 | 100% | 4.29 ms | 26.53 ms | 28.97 ms | 526.41 ms |
| 25 | 3378.20 | 100% | 6.73 ms | 11.47 ms | 25.51 ms | 33.48 ms |
| 50 | 3400.20 | 100% | 14.01 ms | 23.56 ms | 30.21 ms | 47.47 ms |
| 100 | 3423.80 | 100% | 27.54 ms | 46.69 ms | 56.91 ms | 94.43 ms |

解释：

- QPS 明显高于小说列表，符合缓存读路径通常更快的预期；
- 并发 25、50、100 的吞吐基本维持在约 3,400 QPS，说明短窗口内已经接近测试客户端、网关或缓存路径的观测上限；
- 并发 10 时最大延迟达到约 526 ms，但 p95 和 p99 仍较低，说明存在少量长尾请求，不能只看平均或 p50；
- 要确认瓶颈是否在 Redis，需要同时记录 Redis 命中率、慢查询、网络流量和应用缓存指标。

### 5.3 未登录鉴权：`GET /api/auth`

| 并发 | QPS | 预期状态成功率 | p50 | p95 | p99 | 最大延迟 |
| ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 1 | 105.57 | 100% | 13.38 ms | 16.35 ms | 25.13 ms | 26.20 ms |
| 10 | 2089.02 | 100% | 2.55 ms | 20.48 ms | 26.02 ms | 31.57 ms |
| 25 | 3965.69 | 100% | 5.88 ms | 9.92 ms | 18.07 ms | 32.26 ms |
| 50 | 3549.91 | 100% | 13.19 ms | 23.35 ms | 30.24 ms | 52.11 ms |
| 100 | 4090.45 | 100% | 23.02 ms | 38.97 ms | 47.04 ms | 67.02 ms |

解释：

- 该接口返回 `401` 仍被视为成功，因为这是预期鉴权行为；
- 结果表明网关轻量过滤链在本地单实例上吞吐较高；
- 不能据此推导登录后查询、写入、Agent SSE 或模型调用的吞吐；
- 如果要测试真实登录链路，应使用隔离的测试用户和短期 Token，避免触发正式用户的安全策略或污染登录审计数据。

## 6. 当前结果能得出的结论

### 可以确认的结论

1. 本地单实例下，普通小说列表接口在并发 100、短窗口测试中保持了 100% 预期状态码成功率，观测 QPS 约为 `879~951`；
2. 排行榜缓存路径短窗口观测 QPS 约为 `3,400`，但存在少量长尾；
3. 未登录鉴权轻量路径短窗口观测 QPS 约为 `4,090`；
4. 小说列表在并发 50 以后 p95 明显增长，是继续加压时最需要关注的接口；
5. 目前没有足够证据宣称“项目最大 QPS”或“生产可稳定承载多少 QPS”。

### 不能直接得出的结论

- 不能把本地 QPS 直接乘以某个倍数换算成云服务器 QPS；
- 不能用排行榜 QPS 代表带数据库写入的接口；
- 不能用 `/api/auth` 结果代表 Agent 对话能力；
- 不能用 5 秒窗口证明 10 分钟、1 小时长稳运行；
- 不能只凭 100% 成功率判断没有连接池耗尽、GC、慢查询或队列积压。

## 7. 压测脚本和报告的注意事项

当前 PowerShell 脚本位于：

```text
scripts/load-test-qps.ps1
```

脚本默认测试三个接口：小说列表 `size=1`、未登录鉴权和排行榜。历史报告中出现的小说列表 `size=20` 数据来自另一轮 Python 并发探测，因此复测时应把脚本版本、请求参数、测试工具和输出文件一起保存。

建议每次报告记录以下元数据：

```text
提交版本或 Git commit
测试工具版本
Base URL
并发档位
持续时间
请求参数
数据库数据量
Redis 是否预热
服务 JVM 参数
Docker 依赖版本
```

否则两次 QPS 差异无法判断是代码变化、数据量变化、缓存状态变化，还是测试工具变化导致的。

## 8. 建议的正式验收口径

可以先采用以下内部验收标准，而不是追求一个脱离场景的最大值：

| 场景 | 建议验收标准 |
| --- | --- |
| 小说列表 `size=20` | 稳定 10 分钟，错误率 < 1%，p95 < 200 ms |
| 排行榜缓存 | 稳定 10 分钟，错误率 < 0.5%，p95 < 100 ms |
| 未登录鉴权 | 稳定 10 分钟，错误率 < 0.5%，p95 < 100 ms |
| Agent Mock SSE | 首 Token 延迟、完整响应延迟、超时率和限流行为分别统计 |
| 图谱查询 | 统计 PostgreSQL 降级、Neo4j 命中、缓存命中和 p95 |

验收时应使用阶梯加压：

```text
10 并发 → 25 并发 → 50 并发 → 100 并发 → 200 并发 → 400 并发
```

每档至少持续 1~5 分钟；当错误率、p95 或资源利用率超过阈值时停止继续加压，并记录拐点。

## 9. 生产容量评估方法

生产环境应该按照目标 SLO 反推安全 QPS，而不是使用观测峰值：

```text
安全 QPS = 满足错误率和 p95 约束时的稳定 QPS × 安全系数
```

建议安全系数先取 `0.6~0.7`。例如某接口在持续压测中稳定达到 `900 QPS`，且满足错误率和 p95 目标，则初始单实例容量可按约 `540~630 QPS` 规划，再通过多实例和网关限流扩容。

对于 Agent，应该分别计算：

- 普通只读接口 QPS；
- SSE 并发连接数；
- 模型请求并发数；
- 每分钟 Token 消耗；
- 向量检索 QPS；
- 图谱查询 QPS；
- 异步索引队列吞吐。

Agent 的容量瓶颈通常不是单一 QPS，而是模型响应时间、连接数、外部 API 限流、积分消耗和数据库/向量库资源的组合约束。

## 10. 下一步建议

1. 把压测工具统一为 Python 或专业工具（如 k6、JMeter、wrk），避免 PowerShell Job 启动开销影响短窗口结果；
2. 为 `size=1` 和 `size=20` 分别保留独立结果，不混用；
3. 增加 10 分钟稳定性测试和 200/400 并发阶梯测试；
4. 接入 Prometheus，采集 JVM、Tomcat、HikariCP、PostgreSQL、Redis、RabbitMQ、Milvus、Elasticsearch 和 Neo4j 指标；
5. 使用测试用户和 Mock OpenAI-compatible 服务测试 Agent SSE，不调用真实 DeepSeek 做无上限压测；
6. 将每次压测 JSON 原始结果和 Git commit 一起归档，生成趋势图，比较优化前后的 p95、p99 和错误率；
7. 服务器容量最终以持续压测拐点和依赖资源监控为准，而不是以本地短窗口最高 QPS 为准。

## 11. 一句话结论

当前数据可以证明项目普通只读接口在本地单实例短窗口内具备较好的吞吐能力：小说列表约 `879~951 QPS`、排行榜约 `3,400 QPS`、轻量鉴权约 `4,090 QPS`；但这些是测试基线，不是生产承诺。要得到可信的最大承载量，还必须补充长稳压测、阶梯加压、依赖监控和 Agent 独立 Mock 压测。
