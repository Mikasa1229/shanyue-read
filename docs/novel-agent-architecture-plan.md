## 1. 产品定位

小说 Agent 不是通用聊天框，而是理解书籍、理解用户书架、能够给出真实可跳转结果的阅读伙伴。它服务于“发现一本书”和“读懂一本书”两条链路：

- 智能找书：按题材、情绪、节奏、篇幅、人物设定和相似作品等自然语言条件找书。
- 个性化推荐：结合书架、收藏、阅读进度、阅读时长、反馈和热门趋势推荐，避免重复。
- 书籍问答：对已索引书籍回答剧情、人物、伏笔、地点和势力问题，并给出章节证据。
- 人物关系知识图谱：抽取人物、组织、地点、事件及关系演化，按阅读进度展示无剧透关系图。
- 阅读管家：结合动态书架、剧情回忆、线索板和阅读地图，帮助用户持续阅读。

Agent 默认只读。涉及加入书架、收藏、移动书架等写操作时，Agent 只能给出建议，用户必须在前端明确确认。

## 2. 双入口产品形态

### 2.1 全站悬浮 Agent 按钮

悬浮按钮是默认和高频入口，形态接近客服按钮，而不是占据页面布局的侧边栏。

- 固定在右下角，避开 Toast、移动端安全区域与阅读器现有控制按钮。
- 点击后，桌面端弹出锚定按钮的轻量对话窗口，建议宽 380--420px、高 560--680px；移动端采用可拖拽底部弹层。
- 浮窗承载短对话、流式回答、工具进度、1--3 张推荐卡片、章节引用和一度人物关系预览；推荐或图谱依赖不可用时，明确提示快捷洞察降级，不阻断对话或阅读。
- 浮窗默认保留当前页面，并携带经后端验证的轻量上下文，例如当前书的 sourceId、bookUrl、章节序号和书名。
- 浮窗提供“在 Agent 中心继续”入口，把当前会话和页面上下文带到完整页面。
- 未登录用户可以在悬浮窗看到能力说明和试用额度说明；创建会话、发送消息或使用个性化能力时引导登录。

### 2.2 独立 Agent 中心

Agent 中心是独立路由和完整工作台，建议路由为 /agent，不是浮窗的放大版。

| 页面或区域 | 用户能力 |
|---|---|
| 对话工作台 | 多会话历史、会话搜索、长回答、引用展开、导出与删除 |
| 我的发现 | 相似书 DNA、个性化书单、推荐反馈 |
| 书籍洞察 | 完整人物关系图、伏笔雷达、阅读分岔地图、角色访谈 |
| 阅读管家 | 动态书架、剧情回忆、阅读计划、下一本建议 |
| 偏好与隐私 | 剧透等级、题材偏好、会话留存、个性化开关和数据删除 |

运营或管理员配置必须与普通用户设置隔离。可单独提供受 RBAC 保护的 /admin/agent 管理台，用于模型路由、Prompt 版本、知识索引任务、图谱重建、评估集、灰度发布、限流策略和成本监控。模型密钥始终只在服务端 Secret 中管理，不显示或编辑明文。

## 3. 总体架构

| 层级 | 组件 | 职责 |
|---|---|---|
| 快捷入口 | Vue 悬浮按钮与对话浮窗 | 短对话、上下文感知、快捷推荐和跳转 |
| 深度入口 | Vue Agent 中心 | 会话、书籍洞察、阅读管家、偏好与隐私 |
| 网关 | reader-gateway | 路由、Sa-Token 鉴权、传递 X-User-Id |
| Agent 服务 | reader-agent | Spring AI 编排、会话、RAG、图谱、限流、审计和降级 |
| 作品主键层 | reader-novel | 统一作品主键、书源映射、章节版本和内容哈希 |
| 业务事实源 | reader-novel | 书源、书架、收藏、阅读进度和排行 |
| 关键词层 | Elasticsearch | 书名、作者、角色名、章节名和精确短语检索 |
| 语义层 | Milvus | 章节、书籍、角色、事件和用户偏好的向量检索 |
| 图谱层 | Neo4j | 人物、组织、地点、事件、关系和时间线 |
| 异步层 | RabbitMQ | 索引、向量化、实体关系抽取、重试和死信 |
| 数据层 | PostgreSQL、Redis | 会话、任务、反馈、审计、缓存、限流和去重 |
| 模型层 | Chat、Embedding、本地混合 Reranker（外部可选） | 回答、向量化和检索结果精排 |

新增独立 reader-agent 服务，不把模型、RAG 或图谱代码放入 reader-novel：

- reader-novel 继续是书源、书架、收藏、阅读进度和排行的唯一业务事实来源。
- reader-agent 负责 Spring AI 编排、模型调用、知识检索、图谱查询、会话、限流和 AI 观测。
- Agent 只能通过受控内部接口读取小说服务数据，不能跨服务直连小说数据库。
- Gateway 增加 /api/agent/** 路由，默认要求登录；网关传递的 X-User-Id 是用户身份唯一可信来源。

独立服务可以隔离模型超时、Token 成本、长连接和提示词安全问题，避免影响正常阅读主链路。

### 3.1 稳定作品主键与书源映射

现有书源阅读数据以 sourceId 和 bookUrl 为主，同一作品在不同书源中可能有不同 URL、封面、书名别名或章节地址。RAG、向量、图谱和用户进度不能直接以 bookUrl 作为长期主键，因此需要由 reader-novel 建立统一作品层：

| 数据对象 | 建议职责 |
|---|---|
| t_canonical_book | 稳定 canonicalBookId、规范化书名/作者、主元数据、合并状态和置信度 |
| t_book_source_mapping | canonicalBookId 与 sourceId、sourceBookUrl 的映射，以及书源特有封面、目录和版本信息 |
| t_book_content_version | 章节快照、章节序号、内容哈希、抓取时间和索引状态 |

- 书源搜索结果和详情接口逐步返回 canonicalBookId；旧的 sourceId 与 bookUrl 保持兼容，作为定位特定书源内容的映射键。
- 书架、收藏和阅读进度逐步关联 canonicalBookId，同时保留用户实际阅读的书源映射，支持切换到可用书源。历史书架/收藏在首次读取时按已有书源元数据惰性回填；合并作品时级联改指向保留作品，书源删除导致作品失效时清空悬空关联。
- 向量、图谱、线索、事件和索引任务全部以 canonicalBookId 加内容版本为归属，避免同一本书被重复或串书索引。
- 自动合并只对书名、作者、简介和目录特征均高置信度匹配的候选生效；低置信度候选保持分离并进入管理端合并队列，不能仅按书名自动合并。

## 5. LightRAG 图谱与多路证据召回

本项目只采用 LightRAG 作为图谱查询架构，不保留传统 GraphRAG 的全书社区报告、全图遍历或全书摘要拼接。多路召回仍然保留，但它只负责在 LightRAG 确定作品与阅读边界后找回原文证据：Milvus 负责语义候选，Elasticsearch 负责关键词候选，PostgreSQL 负责权威片段兜底，Reranker 只对这些有章节来源的候选排序。

向量检索是 RAG 的必要部分，但不是全部。成熟的书籍问答和找书能力采用“关键词 + 语义 + 图谱”的混合检索：

1. 意图分类：区分找书、剧情问答、人物关系、线索、书架建议和阅读计划。
2. 查询改写：补全书名、角色别名和模糊条件；限制并行查询数量和成本。
3. 多路召回：Elasticsearch 提供精确命中，Milvus 提供语义召回，Neo4j 提供关系邻域和事件链。
4. Rerank 精排：对候选章节、人物和书籍进行最终排序。
5. 上下文组装：去重、控制 Token、保留来源章节和片段定位。
6. 证据型回答：模型只能基于检索上下文回答；无证据时必须说明不确定，禁止虚构剧情或书籍。
7. 剧透过滤：把用户最新阅读章节作为检索硬条件，不能只依赖 Prompt 提醒模型。

### 5.1 Milvus 向量集合

| 集合 | 向量内容 | 核心过滤字段 | 用途 |
|---|---|---|---|
| book_chunk_vectors | 章节语义切片 | bookId、sourceId、chapterIndex、version | 剧情问答、章节引用 |
| book_profile_vectors | 简介、标签、风格摘要 | bookId、题材、作者、状态 | 相似书 DNA 与推荐 |
| character_vectors | 角色描述、别名、行为摘要 | bookId、characterId、chapterIndex | 角色访谈与消歧 |
| event_vectors | 冲突、转折、伏笔、事件摘要 | bookId、eventId、chapterRange | 线索板和阅读分岔地图 |
| user_preference_vectors | 用户偏好摘要 | userId、更新时间、隐私状态 | 动态书架与个性化推荐 |

每条记录必须保存来源、内容哈希、模型版本、索引时间和删除状态。章节内容更新时按内容哈希增量更新，不能全量重嵌入；Embedding 模型版本变更时，即使内容哈希不变，也必须新建索引任务、移除旧向量投影并重嵌入。

### 5.2 切片策略

- 常规文本按语义段落切片，建议约 400--800 中文 Token，保留 10%--15% overlap。
- 对话密集段按场景或人物切换切分，避免切断同一轮对话。
- 同时构建章节摘要、分卷摘要、无剧透全书画像和全剧透全书画像。
- 不将整本外部作品批量送入模型，只传递完成当前请求的最小片段。

## 6. 人物关系图谱与 LightRAG

图谱检索明确采用 **LightRAG 模式**，不采用传统 GraphRAG 作为主查询路径。目标是在保证人物关系、事件因果和伏笔证据可追溯的前提下，降低图谱抽取、多跳检索和上下文拼接的 Token 消耗。

### 6.0 LightRAG 架构约束

- 图数据仍以 Neo4j 为关系投影，PostgreSQL 保留权威节点、边、线索、版本与审核状态；Milvus 保存章节、实体、事件和社区摘要向量。
- 图构建采用增量实体/关系抽取、别名归并和内容哈希幂等，不因单章更新全书重抽取；LLM 图抽取默认关闭，仅在规则抽取无法覆盖且预算允许时按章节按需启用。
- 每本书按已读章节增量维护实体邻域与分层社区摘要（chapter -> arc/volume -> book）；问答必须先识别问题中的可见实体，命中后优先使用实体种子的一至两跳局部关系和 `CHAPTER`/`GRAPH` 卡片。只有局部图与低层卡片均无证据时，才能升级到 `ARC` 卡片。
- 查询固定为“实体识别 -> LightRAG 局部图扩展与低层卡片 -> 阅读边界内的 Milvus/Elasticsearch/PostgreSQL 多路原文证据 -> 去重与统一预算截断 -> Rerank -> 回答”。整本图谱、整书社区卡片和整书原文都禁止进入小说问答上下文；推荐画像单独由 `ProfileVectorService` 维护。
- 图谱关系、事件与线索必须携带章节证据、置信度、模型版本和审核状态；规则抽取的证据可自动通过，LLM 抽取的证据默认 `PENDING` 并由管理台审核。低置信或非 `APPROVED` 内容默认不进入回答上下文、角色/事件向量画像、LightRAG 社区或 Neo4j 局部扩展，前端仅以虚线或“待确认”呈现。
- 社区摘要、实体摘要和事件摘要均缓存并按内容版本失效；同一会话内复用已验证的局部子图，避免重复图查询与重复 Token 消耗。所有 Prompt 输入都必须经统一 Token 预算器，按“系统规则/用户请求 -> 原文证据 -> 局部图 -> 社区 -> 工具结果 -> 会话历史”顺序装配；保存各分段的脱敏 Token 数，不保存 Prompt 正文。

推荐的 LightRAG 图索引资源：

| 资源 | 存储 | 用途 | Token 控制 |
|---|---|---|---|
| 实体/关系/线索 | PostgreSQL + Neo4j | 权威证据与局部邻域查询 | 仅返回已读范围、最多 2 跳 |
| 章节与事件摘要 | PostgreSQL + Milvus | 快速定位相关证据 | 内容哈希增量生成 |
| Arc/分卷社区摘要 | PostgreSQL + Milvus | 长篇结构理解与阅读分岔地图 | 每层摘要限长并缓存 |
| 作品推荐画像 | PostgreSQL + Milvus | 相似书 DNA 与推荐排序 | 由独立作品画像维护，不进入 LightRAG 问答上下文 |

向量库擅长找到相关文本，但不擅长回答多跳关系、伏笔回收和关系随章节演化的问题。图谱以 Neo4j 为主存储，RAG 为每条关系和事件提供可验证的文本证据。

### 6.1 检索边界与候选稳定性

- Milvus 必须在向量 Top-K 前应用 `canonicalBookId == 当前作品` 与 `chapterIndex <= currentChapter` 过滤；过滤表达式由 AST 构造，以支持平台的 long 作品主键并避免文本解析器溢出。
- PostgreSQL 证据兜底最多读取 600 条候选，并按章节倒序、主键正序稳定排序，再交给本地/外部 Reranker；禁止依赖未定义的数据库返回顺序。
- `RetrievalResult` 记录候选总数、最终选中数和各数据源候选数，`RetrievalTrace` 只持久化这些计数、章节编号和来源，不写入问题、Prompt 或小说正文。

### 6.2 图模型

节点包括 Book、Chapter、Character、Organization、Location、Event、Clue。

关系边包括亲属、恋人、师徒、友人、敌对、上下级、同盟、参与、发生于、暗示、回收和导致等。每条关系至少保存：

| 字段 | 含义 |
|---|---|
| type | 关系类型 |
| status | 当前、曾经、推测、已失效、未闭合、已回收 |
| confidence | 抽取置信度 |
| fromChapter | 生效或首次出现章节 |
| toChapter | 失效或回收章节，可为空 |
| evidenceChapterIds | 证据章节 |
| evidenceSnippets | 可定位的证据片段或摘要 |
| sourceModelVersion | 抽取模型版本 |
| reviewStatus | 自动、已确认、已纠正 |

### 6.3 构建流水线

书籍或章节变更触发 RabbitMQ 索引事件，之后依次执行：

1. 清洗、语义切片和版本控制。
2. 生成章节、分卷和全书摘要。
3. 抽取人物、组织、地点、事件和线索。
4. 进行别名消歧与实体合并。
5. 抽取关系、因果和线索状态，绑定章节证据并评分。
6. 写入 Neo4j，同时将切片、角色和事件向量写入 Milvus，将关键词写入 Elasticsearch。

### 6.4 图谱体验

- 悬浮窗口只展示当前人物的一度关系预览或当前章节附近的简短事件导航。
- Agent 中心展示完整关系图、事件图和章节时间轴，支持筛选。
- 每条边和每个事件可展开证据章节，并跳转阅读器。
- 默认按用户阅读进度裁剪图谱，防止节点、关系、线索状态和事件造成剧透。
- 低置信度关系使用虚线或隐藏，不能伪装成确定事实。

## 7. Spring AI 与 Agent 编排

Spring AI 不仅用于发送一次聊天请求，而应成为 AI 接入的统一编排层：

- ChatClient：统一模型调用和流式输出。
- Advisor 链：会话记忆、RAG 上下文、偏好注入、剧透过滤、审计和提示词注入防护。
- VectorStore：对接 Milvus；若目标版本适配不足，通过稳定适配层隔离底层 SDK。
- Tool Calling：以严格 Schema 暴露书源搜索、书籍详情、书架、阅读进度、图谱查询等只读能力。
- Structured Output：推荐卡片、引用和图谱节点边使用 JSON Schema，前端不解析模型 HTML。
- MCP：第二阶段可将内部只读业务工具按 MCP 标准暴露；必须有内网隔离、身份传递、工具白名单和权限审计。

专业化模块由受控编排器调用，不能形成无限递归的多 Agent 对话循环：

| 模块 | 职责 | 数据与工具 |
|---|---|---|
| RecommendationAgent | 相似书 DNA、个性化书单和书荒建议 | 书源、书架、收藏、排行、偏好向量 |
| BookRagAgent | 剧情回忆、人物、伏笔和设定问答 | 混合检索、章节证据、摘要 |
| GraphAgent | 人物关系、线索板、事件和阅读分岔地图 | Neo4j、关系与事件证据检索 |
| BookshelfAgent | 动态书架、阅读顺序和阅读计划 | 书架、进度、阅读时长 |
| CharacterAgent | 角色访谈与别名消歧 | 角色画像、已读章节、关系图 |
| SafetyGuard | 剧透、注入、隐私和越权控制 | 不直接读取业务数据 |

### 7.1 模型接入、用户自配 Key 与平台试用额度

Agent 支持两种模型使用模式，用户可在 Agent 中心的“偏好与隐私”中切换。无论选择哪种模式，RAG、工具调用、剧透过滤和安全护栏始终由 reader-agent 在服务端执行。

| 模式 | 用户体验 | 模型费用与额度 | 服务端约束 |
|---|---|---|---|
| 平台试用 | 直接选择平台提供的测试模型，无需填写 Key | 消耗注册时一次性赠送的试用积分与后续获得的积分 | 严格限制单次 Token、日预算、用户积分消耗和全局预算 |
| 自配模型 Key（BYOK） | 用户选择供应商和模型并保存自己的 Key | 模型调用使用用户自己的供应商额度，不扣平台试用积分 | Agent 仍代理调用，保留 RAG、限流和工具权限；对 Key 全程加密保护 |

平台测试模型初期使用 DeepSeek，但其实际 API Key 只通过服务端 Secret 或环境变量注入，例如 DEEPSEEK_API_KEY。密钥不得出现在前端、数据库明文、Git、Nacos 明文配置、日志、接口响应或管理页面。

BYOK 支持受控供应商预设和经审核的 OpenAI-compatible 端点：默认仅允许官方 DeepSeek/OpenAI HTTPS 主机；自托管端点必须由部署者显式加入 `AGENT_BYOK_ALLOWED_HOSTS`。服务端拒绝 HTTP、私网/未批准主机、URL 用户信息、查询参数和片段，避免 SSRF、钓鱼模型端点和 Key 外泄。

用户保存 Key 的规则：

- 前端仅在创建或更新时通过 HTTPS 提交 Key；查询接口只返回供应商、模型、创建时间和掩码标识。
- reader-agent 使用 AES-256-GCM 加密保存密文；加密主密钥由 Secret 管理，支持轮换，不进入数据库。
- Key 只在一次模型请求的服务端内存中解密使用，不写入日志、Trace、异常堆栈或异步消息。
- 用户可测试、替换、禁用和删除自己的 Key；连通性测试只向用户已保存且受审批端点发送最小独立探测，不创建会话、不写入消息、不扣平台积分；删除后立即不可再用于模型调用。
- 平台试用与 BYOK 都保留基础并发和频率限制，防止工具和检索资源被滥用。

### 7.2 平台积分与试用策略

平台积分是内部试用额度，不是现金、不可提现，充值和支付不在当前范围。积分由 reader-user 统一记账，reader-agent 只能调用内部额度接口，不能直接修改用户积分余额。

- 注册成功时赠送 3 次标准平台 Agent 调用等价积分；这 3 次是一次性新人体验额度，不是每日重置额度。
- 每日签到成功可获得一次积分奖励。
- 有效阅读可获得积分奖励，但必须按服务端统计的有效时长和每日上限结算，不能按客户端上报秒数无限发放。
- 平台模型调用先按预估 Token 预冻结积分，流式结束后按实际 Token 结算；调用失败、取消或模型异常时退还未消耗部分。
- 新人额度耗尽后，平台模型调用从用户自己获得的积分中扣除；不同任务可按实际 Token 和任务等级配置不同积分成本。BYOK 使用用户自己的模型额度，不扣平台模型积分。
- 平台仍设置单次上下文/输出 Token 上限、全局日预算、单用户日积分消耗上限、并发上限和熔断阈值；这些是防刷和成本保护，不代表每日免费发放 3 次。
- 平台模型用量逼近预算或用户积分不足时，优先提示用户签到、完成有效阅读获得积分、使用 BYOK 或等待下一次奖励，而不是静默失败。

防刷要求：签到仅按自然日结算，并以 userId、日期和奖励类型建立唯一幂等约束；阅读积分设日上限、单次最短有效时长、连续页面活跃校验、页面可见性校验、阅读心跳频率限制和异常时长检测。阅读时长由服务端阅读会话累计，客户端上报的秒数只能作为辅助信号，不能直接兑换积分。积分流水采用业务请求幂等键，防止网络重试重复发放或重复扣费。

### 7.3 用户模型与积分数据设计

模型配置归 reader-agent 管理，积分账本归 reader-user 管理：

| 服务 | 表或资源 | 用途 |
|---|---|---|
| reader-agent | t_user_model_config | 供应商、模型、加密 Key 密文、掩码标识、启用状态和更新时间 |
| reader-agent | t_model_usage | 请求、模型、输入/输出 Token、耗时、模式、成本和状态审计 |
| reader-user | t_user_credit_account | 用户可用积分、冻结积分和版本号 |
| reader-user | t_user_credit_ledger | 积分发放、冻结、结算、退款、过期和人工调整流水 |
| Redis | trial quota and rate limit keys | 每用户/全局日额度、并发数和短期幂等控制 |

积分流水来源建议固定为 REGISTER_GRANT、CHECKIN_GRANT、READING_GRANT、AGENT_CREDIT_FREEZE、AGENT_CREDIT_SETTLE、AGENT_CREDIT_REFUND 和 ADMIN_ADJUST。所有与模型请求、签到和阅读行为关联的流水均需携带业务请求 ID。

Agent 请求流程如下：先鉴权并确定模型模式；平台试用模式调用用户服务冻结积分和次数，BYOK 模式验证用户模型配置；随后执行 RAG 和模型流式请求；请求完成后记录 Token 用量，并结算或退款。用户服务可通过签到和阅读事件异步发放积分，Agent 不参与积分铸造。

## 9. 已确认的亮点功能

### 9.1 无剧透剧情回忆胶囊

用户隔几天回到阅读器时，点击悬浮 Agent 按钮即可得到 3--5 条回忆：上次读到哪里、当前冲突、关键人物状态和待解问题。

- 检索条件强制限定为章节序号不大于用户当前阅读进度。
- 回答使用章节摘要和已读范围内的证据片段；不以“后续会怎样”的方式暗示剧情。
- 阅读器中显示为可折叠卡片，支持继续阅读、查看证据和展开为完整回顾。
- 未建立索引的章节只返回安全的书架进度信息，不虚构剧情回顾。

### 9.2 伏笔雷达与线索板

从已读章节抽取未闭合的物品、承诺、人物疑问、目标和事件，形成可查询的线索板。用户可问“这个玉佩第一次出现在哪”“哪些线索还没有解释”。

- 线索节点记录首次出现章节、最近出现章节、关联角色、状态和证据。
- 后续章节出现可验证呼应时，异步更新线索状态为已回收、部分回收或仍未闭合。
- 线索的建立和回收都要带章节证据与置信度；推测和原文事实必须清晰区分。
- 只展示当前用户已读章节范围内的线索状态，避免通过“已回收”本身造成剧透。

### 9.3 相似书 DNA

相似书 DNA 让推荐具备解释性。用户看到的不只是“你可能喜欢”，而是两本书在哪些维度相近。

- 书籍画像提取题材、叙事节奏、主角关系、世界观、情绪曲线、篇幅、阅读难度和读者偏好等维度。
- Milvus 用于召回语义相近的作品，Elasticsearch 补足精确标签和作者条件，Reranker 负责最终排序。
- 前端用 DNA 卡片展示相似维度、不同点和推荐理由；候选书必须来自真实书源或站内书籍。
- 排除已读完成、已明确不喜欢和重复书源候选；用户点击、收藏和跳过会写入反馈闭环。

### 9.4 动态书架管家

动态书架管家不是静态分类，而是根据用户阅读行为把书架转化为可行动的建议。

- 书架可动态分为正在追、适合碎片时间、适合周末沉浸、搁置但值得重启和候选清理等视图。
- 综合最近阅读时间、章节进度、书籍篇幅、读速、阅读时段、偏好向量和用户显式反馈排序。
- 悬浮窗口回答“今晚读什么”“我该接着看哪本”时给出 1--3 个可解释建议。
- Agent 只推荐和排序；移动、删除、加入书架等写操作必须由用户确认。
- 用户可以关闭个性化、删除偏好和手动固定书架分类，确保控制权在用户手中。

### 9.5 角色访谈

角色访谈让用户在不剧透的前提下，以某个角色在当前章节已知的信息理解其选择和动机。

- 用户在人物卡片、关系图或阅读器中选择角色后发问，例如“以他的视角，为什么会这样做”。
- 上下文由已审核且达到置信度阈值的角色画像、已读章节、人物关系边和证据片段构成；模型不能使用未读或待审核的图谱内容。
- 输出明确分为原文事实、基于事实的推断和不足以判断，避免把模型推断伪装成原文。
- 对角色别名先经 Neo4j 和向量检索消歧；无法确认时先追问用户，而不是错误代入角色。

### 9.6 阅读分岔地图

阅读分岔地图以已读内容为边界，将关键事件组织成主线、支线和因果关系，帮助用户理解长篇作品的结构。

- 事件节点关联参与角色、地点、章节范围、因果前置事件和证据。
- 前端提供按章节推进的时间轴；用户可看到“目前有哪些主线在交织”，但不会看到未读事件。
- 悬浮窗口只返回当前章节附近的简短导航；Agent 中心展示完整的可筛选事件图。
- 该功能与人物关系图谱共享 Neo4j 基础设施，但以事件和因果为中心，不只是人物连接图。

## 10. 安全、版权、成本和质量

- 所有 Agent 接口按用户、Gateway 观测到的 IP、会话和模型层级限流，限制单次输入、上下文、工具次数和并发流；Gateway 必须清洗外部伪造的身份与来源标识后再注入可信头。
- 模型 API Key 仅存在于服务端 Secret 或环境变量，不能进入前端、Git 或 Nacos 明文。Gateway 到 Agent 的转发密钥也必须仅以部署 Secret 提供，并在两服务保持一致；不得允许直连 Agent 端口伪造用户头。
- 书源正文、简介、书名和评论都属于不可信外部输入，不能改变系统指令、权限或工具白名单。
- 知识库采用按需、渐进索引：优先索引用户当前阅读、加入书架或主动启用智能解析的作品和章节，避免全量预计算带来的抓取压力、索引成本和内容版本失效。模型请求只传递完成当前任务所需的最小片段；禁止借 Agent 输出整章或整书内容。
- 用户阅读进度是剧透过滤的硬条件；用户可明确选择允许剧透范围。
- 聊天记录应提供清空和过期策略；用户偏好向量必须可删除并按用户隔离。
- 记录调用链、Token、成本、检索命中、工具失败、用户反馈和降级次数，但不在普通日志保存敏感正文。
- 模型、向量库、Neo4j 或索引任务故障时，正常的阅读、搜索、书架和收藏链路不能受影响。
- Milvus 等可选检索依赖必须使用有界 I/O、失败冷却和可观测降级；不可因底层客户端连接阻塞而阻断 Agent SSE。Neo4j 局部查询和关系型权威数据也必须保留可用回退。

## 11. 分阶段实施

### Phase 0：基础决策与平台基线

## 12. 验收标准

- 每张推荐卡片均可追溯到真实书源或站内书籍，不能出现模型虚构作品。
- 书籍问答、剧情回忆、角色访谈、线索和阅读地图必须附带章节来源；没有证据时必须拒答或说明不确定。
- 人物关系、事件因果和线索状态必须携带章节证据、置信度和生效范围。
- 用户阅读到第 N 章时，默认不能检索和展示第 N 章之后的剧情、关系、事件或线索回收。
- 未登录用户无法读取他人的书架、会话、偏好或推荐反馈。
- 在书源、模型、向量库或图谱服务故障时，悬浮窗口和 Agent 中心明确降级，主阅读链路保持可用。
- 索引、关系抽取和删除任务具备幂等、重试、死信与可观测状态。
## 方案 A 修订：本地混合 Reranker 为核心（2026-08-01）

本次架构决策将 Reranker 分为“核心能力”和“可选增强”两层。核心路径严格保持 LightRAG-only：实体识别、受阅读边界约束的局部图扩展、章节/图卡片、多路原文召回后，默认使用服务内无第三方依赖的 `LocalEvidenceReranker`。它融合有界语义召回分数、BM25 风格中文 n-gram 关键词相关性、章节引用/证据质量和多来源交叉佐证，并使用稳定的确定性排序。

外部 OpenAI-compatible Reranker 仅在 `AGENT_RERANKER_ENABLED=true` 且地址与密钥均配置时作为增强或对比实验调用。超时、错误、冷却窗口、未配置和畸形响应都会回退到同一套本地混合排序；外部供应商凭据、联调和压测不再阻塞方案 A 的核心验收，也不会把 DeepSeek Chat 冒充 Reranker。

方案 A 的验收门禁新增 `LocalEvidenceRerankerTest` 的 50 次重复稳定性测试，以及 `scripts/validate-agent-local-reranker.ps1`。外部验证手册保留真实供应商压测流程，但将其标记为可选扩展。该决策不改变 LightRAG 的 36 条局部边预算、`BOOK`/`BOOK_SAFE` 禁止进入问答上下文的约束，也不引入传统 GraphRAG。
