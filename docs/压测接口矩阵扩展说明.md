# 压测接口矩阵扩展说明

## JMeter 容器

JMeter 可以容器化运行。本项目新增了固定版本的构建文件：

```text
perf/jmeter/Dockerfile
perf/jmeter/docker-compose.yml
```

构建镜像：

```powershell
docker compose -f perf/jmeter/docker-compose.yml build
```

运行命令行压测：

```powershell
docker compose -f perf/jmeter/docker-compose.yml run --rm jmeter
```

容器通过 `host.docker.internal:8080` 访问宿主机上的 Reader 网关，结果输出到 `logs/jmeter/`。JMeter 使用 5.6.3，避免每个人本地版本不同导致报告不可比。

当前机器本轮真实扩展数据使用 `scripts/run-real-load-test.py` 生成，因为 JMeter 官方压缩包下载受网络限速影响；这不影响 JMeter 测试计划本身的可复用性，但报告中会明确区分工具来源。

## 本次扩展的接口

### 本地数据库/缓存读路径

```http
GET /api/novels?page=1&size=20
GET /api/novels?page=2&size=20
GET /api/reading/ranking?page=1&size=20
GET /api/book-sources?page=1&size=20
GET /api/novels/1
```

`/api/novels/1` 当前不存在小说时，平台使用统一响应结构，HTTP 状态是 `200`，业务响应码是 `404`，所以不能只用 HTTP 状态码判断业务是否成功。JMeter 计划中已将 HTTP 200 作为传输层预期，业务码应单独加 JSON 断言。

### 未登录安全探测

```http
GET /api/auth
GET /api/bookshelf/hot?top=20
GET /api/agent/infrastructure
```

这些请求预期返回 HTTP 401，测试中按预期鉴权行为计为成功。它们主要用来观察网关和鉴权过滤器，不代表登录后完整业务接口。

### 外部依赖接口：单独统计

```http
GET /api/book-sources/search?keyword=剑来
```

该接口会触发书源搜索，可能访问外部网站或多个书源。实测中出现了 3~10 秒超时和成功率下降，这不是普通数据库接口的性能结论，而是外部网络/书源可用性和超时策略的结果。因此它不能混入本地接口的 QPS 平均值，应作为“外部依赖超时场景”单独报告。

## 为什么不能把所有接口混成一个数字

不同接口的瓶颈不同：

- 小说分页和书源分页依赖 PostgreSQL、分页查询和响应组装；
- 排行榜可能命中 Redis，吞吐明显更高；
- 鉴权接口在过滤器层结束，不会进入业务服务；
- 书源搜索包含外部网络，不受本地数据库 QPS 单独控制；
- Agent SSE 受模型响应时间和长连接数约束，不能用普通 QPS 直接比较。

因此最终报告应按接口类别分别给出：

```text
本地数据库读路径：小说列表、书源分页、详情
本地缓存读路径：排行榜、热门书架
网关鉴权路径：/api/auth、未登录 Agent 探测
外部依赖路径：书源搜索
模型/长连接路径：Agent SSE（另测）
异步处理路径：RabbitMQ + RAG 索引（看队列吞吐，另测）
```

## 当前建议

1. JMeter 容器作为正式、可复现的主工具；
2. Python 执行器保留为本地快速验证和网络受限时的备用工具；
3. 外部书源搜索单独做超时/依赖可用性测试，不纳入普通接口极限 QPS；
4. 为 `/api/book-sources` 重点观察数据库连接池和响应组装耗时；
5. Agent 需要先准备测试用户、Mock 模型和有效 `canonicalBookId`，再另建 SSE 压测计划；
6. JMeter 报告与 JSON 原始结果一起归档，避免只保留截图。
