# 小说智能体面试问题与回答要点

这份文档用于准备面试。回答时应先讲清楚问题和取舍，再讲实现细节，最后说明验证方式。不要只背术语，也不要把可选能力说成默认依赖。

## 一、项目介绍类

### 1. 你先整体介绍一下这个项目

**回答要点**：

- 善阅坊是小说阅读、书友互动和 AI 阅读助手平台。
- 原有系统拆分为 Gateway、用户、小说、点评、互动、签到和 Agent 服务。
- Agent 有悬浮入口和独立 Agent 中心，支持问答、推荐、人物关系图谱、伏笔、无剧透回顾、角色访谈和阅读地图。
- 核心技术是 Spring AI + LightRAG-only + Milvus/Elasticsearch/PostgreSQL 多路证据召回 + Neo4j 图投影。
- 模型支持平台 DeepSeek 和用户自带 API，回答受阅读进度和 Token 预算约束。

**不要这样说**：不要说“完全生产级”“模型自动理解整本书”，因为当前默认 Embedding 是 Hash Embedding，外部 Reranker 也不是核心依赖。

### 2. 你在这个项目中具体负责什么？

可以按四条线回答：

1. 设计作品主键、内容版本和 Agent 索引账本。
2. 完成 `reader-agent` 的会话、模型、RAG、图谱、工具和积分逻辑。
3. 完成 RabbitMQ 异步索引、Neo4j/Milvus/Elasticsearch 投影和故障降级。
4. 完成悬浮 Agent、Agent 中心、管理台、验证脚本和测试门禁。

### 3. 为什么要把 Agent 拆成独立服务？

- 模型调用、检索、索引和会话生命周期与普通阅读接口的资源特征不同。
- Agent 需要独立控制 Token、并发、积分、模型密钥和审计。
- 向量库、图数据库和模型故障不能拖垮普通阅读链路。
- 独立服务后可以单独扩容、灰度模型和部署 Agent 版本。

## 二、架构与数据一致性

### 4. 为什么不直接使用书源 ID，而要设计 `canonicalBookId`？

书源 ID 只代表一个来源，不代表平台中的作品。多来源会导致同书重复索引、引用跳转错误和阅读边界不一致。`canonicalBookId` 作为统一作品主键，书源映射、内容版本、阅读进度、图谱和 Agent 索引都围绕它关联。

### 5. 章节内容更新时，如何避免重复索引？

- 源端先计算章节 SHA-256。
- 索引账本以作品、章节、内容哈希和 Embedding 版本作为幂等指纹。
- 相同 `READY` 版本不重复投递。
- `FAILED` 版本允许后续安全重试。
- Agent 完成后回写源端状态，消息重复消费由数据库唯一约束和幂等写入兜底。

### 6. RabbitMQ 消息重复或乱序怎么办？

不能把 RabbitMQ 当成最终一致性依据。消息只负责触发，最终状态由 PostgreSQL 账本决定。消费者写入时使用内容哈希、唯一键和 `ON CONFLICT` 设计幂等；索引和删除使用不同路由和死信通道；已完成的删除任务收到重复消息时直接跳过。

### 7. 为什么 PostgreSQL、Neo4j、Milvus 和 Elasticsearch 要同时存在？

- PostgreSQL：权威业务数据、章节证据、任务状态和审核状态。
- Neo4j：适合查询人物、事件和关系邻域。
- Milvus：适合语义向量相似度召回。
- Elasticsearch：适合关键词、书名、角色名和短语精确召回。

它们不是四份互相独立的真相，而是“PostgreSQL 权威 + 其它存储投影”。投影失败可以重试或回退，不能让某个投影库成为唯一数据源。

## 三、LightRAG、RAG 与图谱

### 8. LightRAG 和 GraphRAG 有什么区别？你为什么选择 LightRAG？

当前项目只采用 LightRAG-only。核心区别是：

- LightRAG 先识别问题实体，再查询受边界限制的局部图和低层证据。
- 不把整本书、整张图或全书社区报告拼进 Prompt。
- 当前局部图最多扩展两跳、36 条边。
- 只有局部图和章节卡片都缺少证据时，才有限度使用 `ARC` 卡片。

这样可以减少图谱遍历和上下文 Token，同时更容易执行无剧透边界。项目保留 Milvus、Elasticsearch 和 PostgreSQL 的多路原文召回，但这不等于混合 GraphRAG。

### 9. 一次小说问答的完整流程是什么？

```text
校验用户和作品
  -> 从服务端阅读进度得到最大可见章节
  -> 识别可见实体
  -> 查询一至两跳局部图
  -> 选择 CHAPTER / GRAPH / 必要时 ARC 卡片
  -> Milvus、Elasticsearch、PostgreSQL 召回原文证据
  -> 章节边界过滤和证据去重
  -> 本地混合 Reranker 排序
  -> 按系统/历史/图谱/证据/工具预算组装 Prompt
  -> SSE 输出回答、引用、推荐、图谱和完成事件
```

没有足够证据时，系统应拒答或说明不确定，而不是让模型自由补全剧情。

### 10. 为什么不能只用向量数据库？

向量检索擅长找语义相近的文本，但对“谁和谁是什么关系”“事件先后和因果”“伏笔是否已经回收”不够稳定。Neo4j 提供局部关系邻域，RAG 证据提供可引用的章节原文，两者结合才能兼顾关系查询和事实追溯。

### 11. 图谱如何防止模型胡编？

- 每个节点、边、线索都保存章节证据、置信度、抽取来源和审核状态。
- LLM 抽取的实体和关系默认 `PENDING`。
- 管理台审核通过且达到置信度阈值后，才能进入 Neo4j 局部查询、向量画像和读者上下文。
- 证据门禁要求模型声明可以在已索引章节文本中找到支持。
- 同名人物通过身份键、证据和别名消歧，无法确认时不强行合并。

### 12. 36 条边预算有什么作用？

这是一个上下文和延迟保护阈值。高连接人物可能关联大量实体，如果无限扩展，图查询结果和 Prompt 都会膨胀。36 条边使一次回答的图谱上下文可预测，并通过章节证据和排序保留最相关关系。它不是业务上的“最多只能有 36 条关系”，而是一次查询的上下文预算。

### 13. Reranker 是如何工作的？

默认使用服务内的本地混合 Reranker，融合：

- 语义召回分数；
- 中文 n-gram/BM25 风格关键词相关性；
- 章节引用和证据质量；
- 多来源交叉佐证。

外部 OpenAI-compatible Reranker 只是可选增强。超时、异常、格式错误或重复索引时，系统回退到稳定的本地排序，不阻塞 SSE。

## 四、Spring AI、模型和 Agent 能力

### 14. Spring AI 在项目中不是只发一条 HTTP 请求吗？

不是。Spring AI 负责统一模型适配和 Agent 编排，实际使用了 ChatClient、Advisor 链、OpenAI-compatible ChatClient、Function Callback/Tool Calling 和结构化输出。模型选择、上下文预算、证据拼接、工具白名单、SSE 和用量统计在 Agent 服务内完成。

由于需要支持 BYOK，项目没有依赖进程启动时的单一 OpenAI Key，而是按请求构造客户端并选择平台或用户模型。

### 15. 如何实现用户自定义模型？

- 用户保存供应商、模型、Base URL 和加密后的 Key。
- 服务端校验允许的 Host，避免任意内网地址请求。
- API Key 使用服务端密钥加密存储，前端只看到脱敏信息。
- 请求时根据模型路由选择平台配置或用户配置。
- BYOK 不计入平台成本，但仍经过会话、并发和请求限制。

### 16. 为什么使用 SSE，而不是普通 JSON？

小说 Agent 的模型响应可能需要数秒，SSE 可以先返回 `meta`，再持续输出 `delta`、工具状态、推荐和图谱事件，最后以 `done` 或 `error` 结束。用户可以尽早看到回答开始生成，也能分别展示结构化洞察。

### 17. SSE 中途断开如何处理？

- 会话和用户消息先写入数据库。
- 生成过程中限制每个会话的并发请求。
- 模型调用不因客户端重连而自动重复执行。
- 使用会话版本和乐观锁更新完成状态，避免重复写消息和重复结算积分。
- 前端保留已收到的事件，并在需要时重新加载会话。

### 18. MCP 和 Tool Calling 的边界是什么？

MCP 服务只提供只读工具，例如书籍搜索、书籍详情、书架、阅读进度和图谱查询。服务端强制校验 JSON-RPC 生命周期、工具白名单、参数 JSON Schema、调用者身份和剧透边界。写操作不直接暴露给模型，移动书架或删除数据需要由用户明确操作。

## 五、剧透、安全和积分

### 19. 客户端把 `currentChapter=1000` 传过来怎么办？

不信任客户端章节号。Agent 查询小说服务维护的私有阅读进度投影，使用服务端最大已读章节裁剪请求；无法验证时收缩到章节零或安全边界。图谱、线索、胶囊、角色访谈、地图、引用和 MCP 工具都使用同一套规则。

### 20. 如何防止用户绕过 Gateway 直接访问 Agent？

Agent 的浏览器 API 要求 Gateway 注入的共享密钥。Gateway 会删除调用方自带的身份和地址头，再写入可信头；Agent 服务端口没有可信密钥时返回 `404`。因此不能通过直接访问 `8086` 伪造用户身份。

### 21. 积分扣除如何避免模型调用失败仍然扣费？

采用冻结、结算、退款三阶段：调用前冻结，成功后按实际或估算用量结算，模型异常、超时或未执行时退款。流水带业务请求 ID，消息重试和会话重试不能重复结算。

### 22. 为什么新用户是 3 次试用，而不是每天 3 次？

这是产品规则。新用户创建时一次性发放 3 次试用额度，之后依赖签到、阅读奖励或后续充值获得积分。账号、流水和请求幂等共同防止重复发放，短期限流和并发限制用于降低刷额度风险。

## 六、性能、可靠性和运维

### 23. Milvus 或 Neo4j 挂了，Agent 会不会完全不可用？

不会。Milvus 和 Neo4j 的调用使用有界超时、失败冷却和指标记录：

- Milvus 失败时，保留 PostgreSQL/Elasticsearch 证据召回；
- Neo4j 失败时，保留 PostgreSQL 权威图数据和安全的关系型回退；
- 外部 Reranker 失败时，回退本地排序；
- 前端推荐、图谱、胶囊等增强请求独立失败，不隐藏聊天和阅读。

故障注入脚本已经验证 Milvus 或 Neo4j 暂停时 SSE 仍能返回完整结束事件。

### 24. 你如何控制 Token 和模型成本？

- LightRAG 只取局部图，不取整本图。
- 图查询最多 36 条边。
- `BOOK`/`BOOK_SAFE` 不进入问答上下文。
- 系统、历史、图谱、社区、证据、工具分别设置预算。
- 章节证据先去重和裁剪，再进入模型。
- 保存隐私安全的分段 Token 账本，支持按模型和区间查看成本。

### 25. 当前默认 Hash Embedding 会不会影响效果？

会影响生产语义召回质量。Hash Embedding 的优点是无密钥、可重复、适合本地开发和测试；它不能代表真实中文语义模型。生产环境应切换 OpenAI-compatible Embedding，增加新的模型版本和 Milvus 集合，并重新投影既有章节、画像和社区向量。

### 26. 当前系统的扩展瓶颈在哪里？

- 模型调用延迟和供应商限额；
- 首次全量索引的 CPU、网络和模型成本；
- Neo4j 局部图查询和 Milvus 向量检索的并发；
- 单机 Docker 部署下 PostgreSQL、ES、Milvus 和 Neo4j 共享内存；
- Redis 故障时可用性优先的限流策略需要进一步加强。

扩展方式是先把 Agent 服务横向扩展，再将 PostgreSQL、Elasticsearch、Milvus 和 Neo4j 拆到独立节点或托管服务；索引任务通过 RabbitMQ 控制并发。

### 27. 你如何做测试？

- Service 层单元测试覆盖积分、会话、剧透边界、图谱审核、Reranker、工具白名单和索引幂等。
- 使用 Testcontainers 或本地 Docker 验证 PostgreSQL、Redis 等依赖。
- 使用原创十章 fixture 验证图谱抽取、同名实体消歧、引用、线索和剧透拒答。
- 使用脚本验证 Agent 部署、MCP 生命周期、LightRAG Token 预算、依赖故障和 SSE。
- CI 执行后端九模块测试、前端生产构建、Compose 配置和敏感信息扫描。

### 28. 你如何证明不是只写了接口？

可以展示三类证据：

1. 代码：`reader-agent` 服务、Flyway V1-V30、前端 Agent 页面和 Docker Compose。
2. 测试：Agent 测试、原创 fixture、Reranker 稳定性、MCP 和故障注入测试。
3. 运行记录：健康检查、Gateway SSE、1279 章索引完成、Neo4j/Milvus 投影和真实 DeepSeek fixture 验证。

## 七、开放性和反思类问题

### 29. 这个项目最大的技术取舍是什么？

取舍是“以可控上下文和可降级为优先”，而不是追求把所有知识都塞入模型。LightRAG 局部图降低 Token 和延迟，多路原文证据保证引用，PostgreSQL 兜底保证依赖故障时仍有基本能力。代价是索引链路更复杂，需要维护内容版本、投影一致性、审核状态和多种存储。

### 30. 如果重新设计，你会优先改什么？

- 将 Embedding 从 Hash Embedding 切换为真实中文语义模型，并完善重新投影任务。
- 将积分账户初始化改为数据库 `INSERT ... ON CONFLICT`，彻底消除并发创建窗口。
- 对平台额度保护增加 Redis 故障时的数据库原子账本或 fail-closed 策略。
- 在 CI 中增加 PostgreSQL、Milvus、Neo4j、Elasticsearch 和 Gateway 的集成环境。
- 建立更大规模的人工标注问答集，评估引用准确率、剧透拦截率、图谱准确率和推荐质量。

### 31. 这个项目目前算生产级吗？

比较稳妥的回答是：架构和功能已经超过简单 Demo，具备求职展示和小规模部署条件；但默认 Embedding、外部模型质量、长期稳定性、完整生产集成测试和大规模容量验证仍然不足，因此不能声称已经达到成熟商业平台的生产级别。

## 八、反问面试官时可以问什么

- 团队目前更关注 AI 应用落地、模型训练，还是检索和数据工程？
- 线上 RAG 系统如何做数据版本、评估集和回滚？
- 团队对 Agent 的工具权限、审计和安全边界有哪些统一规范？
- 当前更需要提升召回质量、模型成本控制，还是服务稳定性？
