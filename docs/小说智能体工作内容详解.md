# 善阅坊小说智能体：工作内容详解

这份文档用于准备简历讲解和面试表达。内容以当前代码、部署验证记录和测试结果为准，重点说明“为什么这样设计、具体做了什么、如何证明它有效”。

## 一、项目定位与整体架构

善阅坊原本是一个小说阅读和书友互动平台，包含书库、书架、阅读进度、点评、点赞收藏、签到和积分等能力。在此基础上新增 `reader-agent` 服务，将 Agent 作为独立的 AI 应用服务接入现有平台。

Agent 有两个产品入口：

1. 阅读器和全站的悬浮按钮：用于快速提问、回顾当前阅读内容和查看轻量洞察。
2. 独立 Agent 中心：用于完整对话、书籍推荐、人物图谱、伏笔雷达、角色访谈、阅读地图、书架管家和模型配置。

整体调用关系如下：

```text
浏览器
  -> Gateway（登录态、可信用户头、Agent 转发密钥）
  -> reader-agent（会话、模型、LightRAG、工具和积分）
       -> PostgreSQL（权威业务数据和知识证据）
       -> Neo4j（人物、事件、关系的图投影）
       -> Milvus（章节、角色、事件和社区向量）
       -> Elasticsearch（关键词和精确短语召回）
       -> Redis（限流、幂等、缓存和额度控制）
       -> RabbitMQ（章节索引、删除、重试和死信）
       -> OpenAI-compatible 模型（平台 DeepSeek 或用户 BYOK）
```

项目不是把所有能力堆在一个 Controller 里，而是把阅读平台的权威数据、异步索引、检索投影、模型调用和前端体验分层处理。这样做的目的，是让模型或检索依赖故障时，普通阅读、书架和收藏链路仍然可用。

## 二、作品主键、书源和内容版本

### 2.1 要解决的问题

同一本小说可能来自不同书源，书名、作者名甚至章节编号都可能不同。如果直接把书源 ID 当成 Agent 的作品 ID，会出现以下问题：

- 同一本书被重复建立向量和图谱；
- 用户在一个书源上的阅读进度无法约束另一个书源的 Agent 请求；
- 引用和推荐无法跳回真实阅读页面；
- 书源更新时无法判断内容是否真的发生变化。

### 2.2 设计与实现

- 使用 `canonicalBookId` 作为平台内部统一作品主键。
- 使用书源映射表关联不同来源的书籍。
- 使用内容版本记录保存章节内容哈希、抓取时间和索引状态。
- 章节进入 Agent 前先由小说服务计算 SHA-256，并以作品、章节和内容哈希作为幂等依据。
- 索引成功或失败后由 Agent 回写源端账本，源端可以区分 `PENDING`、`READY` 和 `FAILED`。
- 作品合并时将书架、收藏和 Agent 目标迁移到保留作品；删除最后一个书源时先清理版本账本，再异步清理 Agent 投影。

### 2.3 面试中可以强调的点

这部分不是简单加一个字段，而是把“作品身份、内容版本、索引状态和阅读边界”统一起来。Agent 的引用、推荐、图谱和剧透控制都依赖这个统一主键，因此它是整个 Agent 数据正确性的基础。

## 三、LightRAG-only 问答链路

### 3.1 为什么选择 LightRAG

小说问答既需要理解人物关系，又不能把整本书、整张图和大量社区摘要直接塞进 Prompt。传统全图或全书社区检索会产生较大的抽取和上下文成本，也更容易越过用户的阅读边界。

当前实现只采用 LightRAG 模式，不保留传统 GraphRAG 作为问答主路径：

```text
用户问题
  -> 识别可见实体和作品边界
  -> 查询一至两跳局部图（最多 36 条边）
  -> 优先选择 CHAPTER / GRAPH 卡片
  -> 局部图和低层卡片无证据时才考虑 ARC 卡片
  -> Milvus + Elasticsearch + PostgreSQL 多路召回原文证据
  -> 去重、阅读边界过滤、统一 Token 预算
  -> 本地混合 Reranker 排序
  -> 带章节引用的回答或无证据拒答
```

`BOOK` 和 `BOOK_SAFE` 资料不会进入小说问答上下文。推荐画像是独立的向量能力，也不会被当作问答证据使用。

### 3.2 局部图检索

- 先识别问题中的人物、组织、地点或事件实体。
- 只从当前用户已经读到的章节范围中选择实体。
- 查询一至两跳的局部邻域，不进行整本书遍历。
- 对边数设置 36 条预算，防止某个高连接节点把大量关系带入上下文。
- 图节点、关系和线索必须有章节证据、置信度、抽取来源和审核状态。
- 低置信度或未审核的 LLM 抽取内容不能进入读者回答上下文。

### 3.3 多路证据召回

LightRAG 负责确定“应该看哪个局部”，多路召回负责找回“可以引用的原文证据”：

- Milvus：根据 Embedding 召回语义相近的章节切片、角色和事件资料。
- Elasticsearch：根据人物名、关键词、章节名和短语进行精确召回。
- PostgreSQL：保存权威章节切片，作为向量库或关键词库不可用时的兜底。
- 本地混合 Reranker：融合语义分数、中文 n-gram/BM25 风格关键词相关性、章节证据质量和多来源交叉佐证。
- 外部 Reranker：有适配器和失败回退能力，但不是核心依赖；默认仍可只使用本地实现。

### 3.4 Token 控制

系统把系统指令、历史消息、局部图、社区卡片、原文证据和工具结果分成独立预算，并在服务端统一截断。这样可以回答“这次请求为什么消耗这些 Token”，也可以在管理台查看脱敏后的分段统计。

## 四、知识索引和异步处理

### 4.1 索引流程

章节内容准备好后，小说服务发布索引事件，Agent 侧按以下顺序处理：

1. 校验作品、章节、内容哈希和 Embedding 版本。
2. 按段落和句子边界进行语义切片，并保留有界重叠。
3. 保存章节文档和切片记录。
4. 生成 Embedding，并投影到 Milvus。
5. 写入 Elasticsearch 的关键词索引。
6. 使用规则抽取和可选的模型抽取构建人物、事件、关系和伏笔。
7. 将 PostgreSQL 中的权威图数据投影到 Neo4j。
8. 生成 LightRAG 章节/分段卡片和角色、事件、社区画像。
9. 回写源端索引状态，记录成功或失败原因。

### 4.2 RabbitMQ 设计

RabbitMQ 负责把章节读取和知识构建解耦：

- 索引、删除使用不同的路由键和死信通道；
- 消息携带作品、章节、内容哈希和请求 ID；
- 数据库账本负责最终幂等，不能只依赖消息去重；
- 已完成的删除任务再次投递时会被跳过，不会重新打开任务；
- 投影失败可以通过管理接口重试或单独修复证据投影。

### 4.3 当前验证规模

在本地已验证的《剑来》语料规模为：

- `1279/1279` 章节状态为 `READY`；
- `1279/1279` Agent 索引任务完成；
- `20472` 个章节切片；
- PostgreSQL 图谱权威数据包含 `26893` 个节点和 `399953` 条边；
- Neo4j 完成同规模的有界批量投影。

这些数字适合在面试中作为“索引链路实际跑过”的证据，但不要把它表达成线上生产规模。

## 五、模型接入、BYOK 和积分

### 5.1 统一模型适配

Agent 通过 OpenAI-compatible 适配层连接平台模型和用户模型：

- 平台模式使用服务端配置的 DeepSeek 模型；
- BYOK 模式保存用户自己的供应商、模型、Base URL 和加密后的 API Key；
- API Key 只在服务端使用，不进入前端、Git、普通日志或接口响应；
- 模型路由可以根据场景和灰度比例选择不同模型；
- 模型没有返回有效用量时，系统会标记为 `ESTIMATED`，不会伪装成供应商真实用量。

### 5.2 积分账本

平台模型不是直接扣一个计数器，而是通过积分账户和流水完成：

1. 请求开始前冻结积分。
2. 模型完成后根据实际或估算 Token 结算。
3. 模型调用失败或未执行时退款。
4. 新用户创建时只发放一次 3 次试用额度。
5. 签到和阅读奖励通过用户服务产生流水，Agent 不直接铸造积分。

BYOK 请求不计入平台模型成本，但仍然受到会话、并发和请求频率限制。

## 六、产品功能与前端工作

### 6.1 悬浮 Agent

- 全站显示悬浮入口，阅读器内自动携带当前作品和章节上下文。
- 点击后打开轻量对话弹窗，不打断主要阅读流程。
- 推荐、图谱、剧情胶囊等洞察分别请求，单个能力失败不会隐藏其它结果。
- 引用可以跳回经过校验的真实书源和章节。

### 6.2 Agent 中心

Agent 中心提供完整会话、模型设置、偏好设置、书架分组和洞察页面。初始化请求将“对话和模型”等核心能力与“推荐、阅读计划、基础设施状态”等增强能力分开，增强接口失败时仍然可以继续聊天。

### 6.3 六类特色能力

- 无剧透剧情回忆胶囊：只使用用户已读范围内的章节摘要和证据。
- 伏笔雷达与线索板：展示线索的首次出现、关联角色、状态和证据章节。
- 相似书 DNA：以题材、叙事节奏、人物关系、情绪曲线等维度解释推荐原因。
- 动态书架管家：根据阅读进度、阅读时段和偏好给出书架分组与下一本建议。
- 角色访谈：只允许选择已审核、达到置信度阈值并且在阅读边界内可见的角色。
- 阅读分岔地图：以事件、因果和章节边界组织主线、支线和分支，不展示用户尚未读到的内容。

## 七、安全、剧透和工具调用

### 7.1 Gateway-Agent 边界

浏览器不能直接伪造用户请求头访问 Agent。Gateway 会清理外部伪造的身份头，并注入内部可信用户 ID、来源地址和 Gateway-Agent 共享密钥；Agent 服务端口收到不带可信密钥的浏览器请求时返回 `404`。

### 7.2 剧透边界

客户端提交的章节号不是可信来源。Agent 会从小说服务的私有阅读进度投影中校验并裁剪章节边界；无法验证时默认收缩到安全边界。图谱、线索、角色访谈、阅读地图、引用和 MCP 工具都使用同一套边界规则。

### 7.3 MCP 和 Tool Calling

当前 MCP 服务只提供书籍搜索、书籍详情、书架、阅读进度和知识图谱等只读工具。服务端校验 JSON-RPC 生命周期、工具白名单、参数类型、章节范围和调用者身份，不把写操作工具直接暴露给模型。

## 八、可观测性、测试与降级

- Prometheus 记录请求、Token、模型成本、检索命中、Reranker 成功/回退、Milvus/Neo4j 故障和限流指标。
- OpenTelemetry 和 Jaeger 记录模型、检索和工具调用链路，但不记录 API Key、用户正文和完整 Prompt。
- Milvus、Neo4j、Reranker 使用有界超时和失败冷却；故障时回退到 PostgreSQL、关系型图数据或本地精排。
- Agent 服务有图谱审核队列、索引运维、删除重试、Prompt 版本、模型路由、成本分析和离线评估入口。
- 当前后端九模块回归测试、Agent 测试、前端生产构建、Docker Compose 配置检查和 `git diff --check` 均已纳入验证流程。

## 九、面试时需要主动说明的边界

为了避免过度包装，建议主动说明以下事实：

1. 默认 Embedding 是无密钥运行的 Hash Embedding；生产环境需要切换真实的 OpenAI-compatible Embedding 并重新投影向量。
2. 外部 Reranker 是可选增强，默认核心路径使用本地混合 Reranker。
3. 当前已完成本地完整运行和原创 fixture 验证，但不把本地验证等同于长期生产 SLA。
4. CI 主要是构建、单元测试和配置门禁，真实模型、向量库和完整 Gateway 链路仍需要部署环境持续验收。
5. 《剑来》正文和向量数据不提交到 Git，新环境需要重新配置书源、爬取和索引。

## 十、一分钟项目介绍模板

“这是我独立开发的小说阅读与 AI 阅读助手平台。原有平台采用 Spring Cloud 微服务架构，我新增了独立的 `reader-agent` 服务。Agent 不是简单调用一次大模型，而是采用 LightRAG-only 的检索链路：先根据用户已读范围识别实体并扩展一至两跳局部图，再通过 Milvus、Elasticsearch 和 PostgreSQL 召回有章节来源的原文证据，最后使用本地混合 Reranker 和 Token 预算生成带引用的回答。图谱关系投影到 Neo4j，索引通过 RabbitMQ 异步处理，并提供 SSE、BYOK、MCP 只读工具、积分账本、剧透边界和故障降级。前端有悬浮 Agent 和独立 Agent 中心，支持无剧透回顾、伏笔雷达、相似书 DNA、角色访谈和阅读分岔地图。”
