# 单实例真实接口极限压测报告

## 1. 测试结论

本次在本机运行中的 Reader 单实例服务上，对三个只读/轻量接口进行了真实 HTTP 阶梯压测。测试覆盖并发 `1、10、25、50、100、200、400、800`，每档持续 5 秒。

按本次 Demo 验收口径：

```text
错误率 < 1%
p95 < 200 ms
p99 < 500 ms
```

结论如下：

| 接口 | 最大满足上述延迟口径的测试档位 | 该档观测 QPS | p95 | p99 | 800 并发结果 |
| --- | ---: | ---: | ---: | ---: | --- |
| 小说列表 `size=20` | 100 并发 | 1121.20 | 124.15 ms | 147.76 ms | p95 904.96 ms，明显超出体验阈值 |
| 阅读排行榜 `size=20` | 400 并发 | 3592.60 | 123.86 ms | 153.90 ms | p95 135.06 ms，仍未出现错误 |
| 未登录鉴权探测 | 800 并发 | 3597.40 | 136.94 ms | 170.95 ms | 仍未出现错误，但吞吐下降 |

因此，本次没有测到 HTTP 错误意义上的“崩溃极限”，但测到了用户体验意义上的延迟拐点：

- 小说列表在 200 并发开始超过 p95 200 ms，400 并发明显恶化，800 并发 p95 接近 905 ms；
- 排行榜缓存路径在 800 并发仍保持 100% 预期状态码，但吞吐从约 3,600 QPS 降到约 3,227 QPS；
- 鉴权轻量路径在 800 并发仍保持 100% 预期 `401`，但相比 50 并发的约 4,092 QPS 已经出现吞吐回落。

## 2. 测试环境和范围

| 项目 | 值 |
| --- | --- |
| 测试时间 | 2026-08-05（Asia/Shanghai） |
| 服务入口 | `http://localhost:8080` |
| 部署 | 本机 Spring Boot 微服务单实例 + Docker 依赖 |
| Java | OpenJDK 17 |
| 测试数据 | 当前本地数据库状态；小说列表当前返回空记录，排行榜当前为空 |
| 测试工具 | Python 3.13 线程池真实 HTTP 执行器；同时生成了可用的 JMeter 5.6.3 测试计划 |
| 每档时长 | 5 秒 |
| 并发档位 | 1、10、25、50、100、200、400、800 |
| 请求方式 | GET，读取完整响应体，保留连接复用 |

本次压测只包含不改变业务数据的接口：

```http
GET /api/novels?page=1&size=20
GET /api/reading/ranking?page=1&size=20
GET /api/auth
```

其中 `/api/auth` 返回 `401` 是预期的未登录鉴权结果，因此在测试中计为成功，而不是错误。

没有把真实 DeepSeek、Agent SSE、积分扣减、图谱重建和异步索引加入极限循环，避免消耗模型额度、建立大量长连接或污染业务数据。Agent 这些场景应使用 Mock 模型和隔离测试用户另测。

## 3. 测试执行方式

### 3.1 真实执行器

实际执行命令：

```powershell
python scripts/run-real-load-test.py `
  --base-url http://localhost:8080 `
  --duration 5 `
  --stages 1,10,25,50,100,200,400 `
  --output logs/real-load-test.json

python scripts/run-real-load-test.py `
  --base-url http://localhost:8080 `
  --duration 5 `
  --stages 800 `
  --output logs/real-load-test-800.json
```

执行器使用线程池产生并发，通过真实 HTTP 请求访问网关，读取完整响应，并统计：

- 总请求数；
- 预期状态码成功数；
- 错误率；
- QPS 和成功 QPS；
- p50、p95、p99；
- 最大延迟；
- 连接异常和超时类型。

### 3.2 JMeter 计划

已新增可导入 Apache JMeter 5.6.3 的测试计划：

```text
perf/jmeter/reader-api-step-load.jmx
perf/jmeter/reader-api-endpoints.csv
```

当前机器没有可用的 JMeter 安装，官方压缩包下载也受到网络限速影响，因此本次真实数据由等价的本地 HTTP 执行器完成。JMeter 计划保留了相同的目标接口、状态码和并发参数，安装 JMeter 后可直接复测。

## 4. 详细结果：小说列表

接口：`GET /api/novels?page=1&size=20`

| 并发 | 请求数 | QPS | 成功率 | p50 | p95 | p99 | 最大延迟 |
| ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 1 | 388 | 77.60 | 100% | 14.92 ms | 27.83 ms | 30.01 ms | 129.27 ms |
| 10 | 4237 | 847.40 | 100% | 6.26 ms | 30.16 ms | 33.16 ms | 43.32 ms |
| 25 | 5258 | 1051.60 | 100% | 21.34 ms | 42.37 ms | 50.19 ms | 63.41 ms |
| 50 | 5722 | 1144.40 | 100% | 41.47 ms | 63.54 ms | 71.07 ms | 93.50 ms |
| 100 | 5606 | 1121.20 | 100% | 86.26 ms | 124.15 ms | 147.76 ms | 235.90 ms |
| 200 | 5285 | 1057.00 | 100% | 190.08 ms | 235.87 ms | 317.01 ms | 503.94 ms |
| 400 | 5654 | 1130.80 | 100% | 354.18 ms | 491.01 ms | 531.16 ms | 805.03 ms |
| 800 | 4849 | 969.80 | 100% | 824.00 ms | 904.96 ms | 935.27 ms | 1200.98 ms |

分析：

- 10 到 50 并发期间，吞吐从 847 QPS 增加到 1144 QPS；
- 100 并发仍保持 p95 124 ms，符合本次 Demo 的延迟口径；
- 200 并发时 p95 达到 235.87 ms，说明从 100 到 200 并发出现明显排队或资源竞争；
- 400 并发时 p95 接近 491 ms，800 并发时 p95 超过 900 ms；
- QPS 没有随并发线性增长，说明接口已进入饱和区，继续加并发主要增加等待，不会带来有效吞吐提升。

本接口本次的“最大稳定体验档位”建议记为：

```text
100 并发，约 1121 QPS，p95 124.15 ms，错误率 0%
```

如果只以错误率定义极限，则 800 并发仍未失败；但这个结论没有实际用户体验价值，因此不应把 800 并发写成生产承载能力。

## 5. 详细结果：阅读排行榜

| 1 | 965 | 193.00 | 100% | 1.90 ms | 24.49 ms | 27.32 ms | 28.94 ms |
| 10 | 8158 | 1631.60 | 100% | 3.05 ms | 23.91 ms | 27.30 ms | 29.17 ms |
| 25 | 18835 | 3767.00 | 100% | 6.35 ms | 9.32 ms | 14.84 ms | 32.65 ms |
| 50 | 18027 | 3605.40 | 100% | 13.35 ms | 21.30 ms | 26.24 ms | 46.55 ms |
| 100 | 18061 | 3612.20 | 100% | 26.30 ms | 42.74 ms | 50.94 ms | 91.99 ms |
| 200 | 17077 | 3415.40 | 100% | 51.38 ms | 89.92 ms | 112.37 ms | 204.23 ms |
| 400 | 17963 | 3592.60 | 100% | 61.71 ms | 123.86 ms | 153.90 ms | 260.14 ms |
| 800 | 16136 | 3227.20 | 100% | 67.70 ms | 135.06 ms | 167.83 ms | 284.08 ms |

分析：

- 25 并发达到约 3767 QPS，说明该接口很可能主要受缓存读路径支撑；
- 100 并发时 p95 仍只有 42.74 ms；
- 400 和 800 并发时吞吐开始下降，说明瓶颈可能转移到网关、客户端调度、Redis、线程池或本机 CPU；
- 800 并发仍满足 p95 200 ms 和 p99 500 ms 的本次口径，但这只是 5 秒短窗口结果，不代表长稳结果。

本接口本次的最大稳定体验档位可以记录为：

```text
800 并发，约 3227 QPS，p95 135.06 ms，错误率 0%
```

但如果要给生产留余量，更建议按 400 并发、约 3593 QPS 或更低的安全负载规划。

## 7. 性能拐点

本次最清晰的拐点出现在小说列表：

```text
100 并发：p95 124.15 ms，仍在目标内
200 并发：p95 235.87 ms，超过目标
```

因此可以把小说列表的单实例体验拐点定位在 `100~200` 并发之间。对面试展示，建议表述为：

> 在当前本地单实例、空数据集的 Demo 环境中，小说列表在约 100 并发、1121 QPS 时仍满足 p95 124 ms；提升到 200 并发后 p95 上升到 236 ms，出现明显延迟拐点。该接口的建议稳定运行区间应低于 200 并发，而不是把 800 并发的短时无错误当成容量上限。

## 8. 结果可信度和局限性

### 可信之处

- 请求真实经过 `localhost:8080` 网关；
- 读取完整 HTTP 响应体；
- 每档都统计了完整延迟分布；
- 结果保存为原始 JSON，可重复分析；
- 预期 `200/401` 状态码明确区分。

### 局限性

- 每档只有 5 秒，不能代表 10 分钟或 1 小时长稳；
- 当前小说和排行榜数据量很小，且接口返回空记录，不能代表真实大数据量查询；
- 测试工具运行在服务同一台机器，会和服务争抢 CPU；
- 没有本次同步采集 JVM、CPU、Hikari、PostgreSQL 和 Redis 时间序列；
- Python 执行器是 JMeter 不可用时的本地等价执行器，不应在简历中声称本轮结果由 JMeter 生成；
- Agent 模型、SSE、向量检索和图谱重建没有纳入本轮极限测试。

因此，本报告结论应称为：

```text
本地单实例短窗口真实性能基线和延迟拐点
```

而不是：

```text
生产环境最大 QPS 保证值
```

## 11. 面试表达

> 这是一个单实例 Demo，所以我没有把本地压测包装成生产容量。我通过网关对小说列表、排行榜和鉴权接口做了 1 到 800 并发的阶梯测试，每档 5 秒，统计 QPS、成功率、p50、p95 和 p99。小说列表在 100 并发约 1121 QPS 时 p95 为 124 ms，200 并发时 p95 升到 236 ms，说明 100 到 200 并发之间出现延迟拐点；排行榜缓存路径在 800 并发仍保持 100% 成功率、约 3227 QPS。Agent 模型调用没有直接压真实 API，而是计划使用 Mock 模型单独测试 SSE 首 Token 延迟和连接数。下一步如果要做生产容量评估，还需要长稳压测、真实数据量和 Prometheus 资源监控。
