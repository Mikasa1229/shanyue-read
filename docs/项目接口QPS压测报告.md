# 项目接口 QPS 压测报告

测试日期：2026-08-04  
测试环境：Windows 本地开发机、JDK 17、Spring Boot 微服务、Docker 中间件、单实例部署  
测试入口：`http://localhost:8080` 网关  
测试工具：`scripts/load-test-qps.ps1` 及本次 Python 并发探测脚本

## 1. 测试范围

本次先测试不消耗模型额度、不会产生写入副作用的 HTTP 接口：

| 接口 | 说明 |
| --- | --- |
| `GET /api/novels?page=1&size=1` | 小说列表，验证网关、小说服务、PostgreSQL/缓存链路 |
| `GET /api/novels?page=2&size=20` | 较大分页返回，观察响应体和查询链路变化 |
| `GET /api/reading/ranking?page=1&size=20` | 阅读排行榜，验证 Redis/用户信息组装链路 |
| `GET /api/auth` | 未登录鉴权探测，主要测网关鉴权和轻量 HTTP 处理能力 |

Agent 的聊天 SSE、模型测试、推荐生成和图谱重建没有纳入高并发循环：这些接口会触发模型调用、积分扣减、数据库写入或长连接，直接用大规模无控制压测会消耗 DeepSeek 配额并污染业务数据。它们应使用固定测试用户、模型 Mock 和独立测试语料进行单独压测。

## 3. 结论

- 在当前本地单实例环境下，小说列表接口在 100 并发、约 `879~951 QPS` 时仍然 100% 成功；但 p95 已升至 `135~156 ms`，继续加压应重点观察数据库连接池、Tomcat 工作线程和 PostgreSQL CPU。
- 排行榜接口在 100 并发、约 `3424 QPS` 时仍然 100% 成功，说明当前缓存路径吞吐较高；最大延迟偶发尖峰说明仍需用更长的 1~5 分钟测试观察缓存失效和 GC。
- 鉴权探测接口约 `4090 QPS` 仍无错误，只能代表轻量网关处理能力，不能代表业务接口或 Agent 能力。
- 本次没有得到“项目最大 QPS”这个绝对值。最大 QPS 必须定义验收门槛，例如“错误率 < 1%、p95 < 200 ms、持续 10 分钟”，再逐级加压到出现拐点。

## 4. Agent 接口的特殊限制

Agent 浏览器接口必须通过网关访问；直接请求 `8086/api/agent/*` 被安全过滤器返回 404 是预期行为。聊天接口还受以下限制：

- 每个会话默认只允许一个并发生成请求；
- 用户/IP 速率限制默认分别为 20/分钟和 60/分钟；
- 平台模型请求会扣除积分并受每日平台额度限制；
- SSE 请求会长期占用连接和异步执行资源；
- 图谱、Milvus、Elasticsearch、Neo4j 和模型调用会把吞吐瓶颈转移到外部依赖。

因此 Agent QPS 需要另建“Mock 模型 + 测试用户 + 独立数据库”的压测场景，不能用真实 DeepSeek API 做无上限压力测试。

## 5. 复测命令

```powershell
pwsh ./scripts/load-test-qps.ps1 -BaseUrl http://localhost:8080 -DurationSeconds 10 -OutputPath logs/qps-load-test.json
```

建议生产容量评估至少增加：

1. 10 分钟稳定性测试；
2. 逐级并发到 200、400、800；
3. Prometheus CPU、堆内存、GC、Tomcat 线程、Hikari 连接池、Redis 命中率、PostgreSQL 慢查询同步采样；
4. Agent 使用 Mock OpenAI-compatible 服务测试 SSE 首字节延迟、完整响应延迟、错误率和限流行为；
5. 使用独立测试数据，不要污染正式用户、积分和阅读记录。
